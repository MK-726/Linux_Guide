# Firewall Concepts

## Overview

A **firewall** controls which network traffic is allowed to reach a system or pass through it. On Linux, packet filtering is built into the kernel (**netfilter**). The commands and tools you use (nftables, iptables, firewalld, UFW) are different front ends to the same kernel mechanism. Understanding the concepts lets you work with any of them.

## Key concepts

### Firewall types

| Type | Description |
|------|-------------|
| **Host firewall** | Runs on the server itself and protects that host. Linux firewalls are usually this |
| **Network firewall** | A device between networks (hardware appliance, Linux router) |
| **Cloud security group / network ACL** | Firewall rules in the cloud platform, applied outside your VM |
| **Application firewall (WAF)** | Understands application protocols (HTTP) |

Use **several layers**. A host firewall remains important even when a network firewall exists.

### Stateless vs. stateful

- A **stateless** filter judges each packet alone (source, destination, port).
- A **stateful** filter tracks **connections** (connection tracking, "conntrack"). Replies to allowed outgoing connections are allowed automatically, and unrelated incoming packets are dropped.

Linux is stateful. Typical states:

| State | Meaning |
|-------|---------|
| `new` | First packet of a new connection |
| `established` | Part of a connection already seen in both directions |
| `related` | A new connection related to an existing one (for example, an ICMP error or FTP data) |
| `invalid` | Does not fit any known connection (usually dropped) |

### Netfilter hooks, tables, and chains

Packets pass through **hook points** in the kernel. Rules are organized in **tables** and **chains**.

```
                         ┌────────── local process ──────────┐
                         │                                    │
 incoming ─► PREROUTING ─┤ routing decision ├─► INPUT ──► process ──► OUTPUT ─► POSTROUTING ─► outgoing
                         │        │                                              ▲
                         │        └──────────► FORWARD ──────────────────────────┘
                         └───────────────────────────────────────────────────────┘
```

| Hook / chain | Packets handled |
|--------------|-----------------|
| **prerouting** | Everything arriving, before the routing decision (DNAT happens here) |
| **input** | Destined for **this host** |
| **forward** | Passing **through** this host (routing between interfaces) |
| **output** | Generated by **this host** |
| **postrouting** | Everything leaving, after routing (SNAT / masquerade here) |

### Rules, policies, and verdicts

A rule has **matches** (protocol, port, address, interface, state) and a **verdict**:

| Verdict | Effect |
|---------|--------|
| `accept` | Allow |
| `drop` | Silently discard (the sender waits and times out) |
| `reject` | Discard and tell the sender (TCP RST or ICMP unreachable). Faster failure, reveals that a firewall exists |
| `log` | Write a log entry (then continue) |
| `jump` / `goto` | Continue in another chain |
| `return` | Go back to the calling chain |

Each **base chain** has a **default policy** (`accept` or `drop`) for packets that match no rule. Rules are checked **in order**. The first matching terminal rule decides.

### Default deny

The standard secure design:

1. **Policy: drop** on `input` (and `forward`).
2. Allow **established and related** traffic.
3. Allow **loopback**.
4. Allow **ICMP** and **ICMPv6** (needed for diagnostics, path MTU, IPv6 neighbor discovery).
5. Allow only the **services you provide**, from the sources that need them (for example, SSH from an admin network).
6. Optionally log and drop the rest.

Outgoing traffic is often allowed by default on servers. High-security environments also restrict **egress** (outgoing) traffic to what is needed, which limits data theft and malware command channels.

### NAT

| Type | Purpose | Chain |
|------|---------|-------|
| **SNAT** / **masquerade** | Rewrite the **source** address (private hosts share one public address). `masquerade` is for dynamic addresses | postrouting |
| **DNAT** / port forwarding | Rewrite the **destination** (publish an internal server on a public port) | prerouting |
| **Redirect** | DNAT to the local host (transparent proxy) | prerouting / output |

NAT router requirements: `net.ipv4.ip_forward=1`, correct routes, and `forward` chain rules.

### Zones (firewalld concept)

A **zone** is a trust level assigned to an interface or source network (for example `public`, `internal`, `trusted`). Each zone has its own allowed services. See [firewalld and UFW](08-firewalld-and-ufw.md).

### Tools and how they relate

```
   ┌────────────────────────────────────────────────────────┐
   │ Friendly front ends:  firewalld   ufw   (cloud tools)  │
   ├────────────────────────────────────────────────────────┤
   │ Rule languages:       nftables (nft)   iptables(-nft)  │
   ├────────────────────────────────────────────────────────┤
   │ Kernel:               netfilter (nf_tables backend)    │
   └────────────────────────────────────────────────────────┘
```

| Tool | Notes |
|------|-------|
| **nftables** (`nft`) | The modern framework. Replaces iptables, ip6tables, arptables, ebtables |
| **iptables** | Legacy syntax. On current systems `iptables` is often a **compatibility layer** that creates nftables rules (`iptables-nft`) |
| **firewalld** | Default on RHEL-based and SUSE-based systems. Zones, services, runtime/permanent. Uses nftables |
| **UFW** | "Uncomplicated Firewall". Ubuntu's simple front end. Uses iptables/nftables |
| **Cloud security groups** | Outside the VM. Check them too |

### Defaults by distribution

| Distribution | Default firewall tooling |
|--------------|--------------------------|
| RHEL, Fedora, Rocky, AlmaLinux | **firewalld** (enabled) |
| SLES, openSUSE | **firewalld** (replaced SuSEfirewall2) |
| Ubuntu | **UFW** installed, **disabled** by default |
| Debian | No firewall enabled by default. `nftables` available |

> [!IMPORTANT]
> Use **one** firewall manager. Do not mix `firewalld`, `ufw`, and hand-written `nft`/`iptables` rules on the same host. They overwrite each other or produce confusing results.

## Commands

See what is active:

```console
# nft list ruleset | head -30                  # nftables (includes rules created by firewalld, ufw, iptables-nft)
# iptables -S 2>/dev/null | head               # iptables view
# iptables --version
iptables v1.8.10 (nf_tables)                   # (nf_tables) = compatibility layer; (legacy) = old backend
# systemctl is-active firewalld ufw nftables
# firewall-cmd --state                         # firewalld
# ufw status verbose                           # UFW
# conntrack -L | head                          # tracked connections (package conntrack)
# sysctl net.netfilter.nf_conntrack_count net.netfilter.nf_conntrack_max
```

## Design checklist

1. Know what must be reachable (ports, protocols, source networks).
2. Default deny incoming.
3. Allow SSH **only** from admin sources when possible.
4. Cover **IPv4 and IPv6**.
5. Keep ICMP and ICMPv6 (limited), because blocking all ICMP breaks path MTU discovery and IPv6.
6. Log and monitor drops (rate-limited).
7. Test from outside, not only from the server.
8. Document the rules and keep them in version control or configuration management.
9. Plan **rollback** before changing a remote firewall.

## Common pitfalls

- **Locking yourself out over SSH.** Allow SSH **before** enabling a default-deny policy, keep a session open, have console access, or schedule a rollback (`at now + 5 minutes` to flush or restore rules).
- **Forgetting IPv6.** Rules for IPv4 do not protect IPv6. Use the `inet` family in nftables, `ip6tables`, or make sure the front end handles both.
- **Mixing firewall managers.** Pick one.
- **Rule order mistakes.** A broad `accept` above a specific `drop` makes the `drop` useless.
- **Blocking all ICMP.** Breaks path MTU discovery and IPv6. Allow the needed types.
- **Docker and Kubernetes** insert their own rules. Published container ports can **bypass** UFW and firewalld input rules. Review `nft list ruleset` and use the DOCKER-USER chain or bind published ports to loopback.
- **Runtime vs. persistent confusion.** Rules added at the command line are lost at reboot unless saved.
- **`reject` vs. `drop`.** `drop` hides the host but slows clients and troubleshooting. Use `reject` for internal networks and `drop` on exposed interfaces.
- **Assuming a firewall solves everything.** Patch services, authenticate users, and minimize exposed services.
- **Cloud rules ignored.** Both the host firewall and the cloud security group must allow the traffic.
